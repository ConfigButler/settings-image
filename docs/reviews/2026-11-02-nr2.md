# Review nr2: the safety policy and the input layout (2026-11-02)

_A second review of the format contract, the implementation, the tests, the CLI, the Action and
the publishing flow, after SOPS support landed. Its three validation gaps were reproduced with
temporary inputs. The maintainer's answer was a new layout, v2 ([format-v2.md](../format-v2.md)),
rather than another heuristic on top of v1. Each finding below has its decision._

## What the review found

**Assessment:** the core image design is strong; the Secret policy needed tightening before anyone
relies on it to prevent accidental publication. ConfigMap files are useful, and carrying custom
resources without requiring CRDs is a sensible scope.

### 1. High: a SOPS-encrypted file could hold a plaintext Secret payload

The SOPS walker checked only the values the file's own rule selects, and the Secret check accepted
any document in a file with SOPS metadata. This was accepted:

```yaml
kind: Secret
stringData:
  password: plain
unrelated: ENC[...]
sops:
  encrypted_regex: ^unrelated$
  mac: ENC[...]
```

A legitimate SOPS file whose rule selects the wrong fields does the same: SOPS supports selective
encryption, so "SOPS-encrypted file" does not mean "every sensitive value is encrypted".

**Decision:** every non-empty `data` and `stringData` value of a Secret must be ciphertext,
whatever the SOPS rule says; for a sensitive kind, every field outside `apiVersion`, `kind` and
`metadata`. The committed fixture `testdata/sops/unencrypted-regex.yaml`, written by `sops`
itself, is now refused for exactly this.

### 2. High: `kind: List` bypassed the Secret check

Only the outer document was inspected, so a `List` holding a plaintext Secret was accepted.

**Decision:** under `resources/`, a core-group `…List` (`List`, `SecretList`, `ConfigMapList`) and
the list of a sensitive kind are refused. Each item goes in its own document, and is checked.

### 3. Medium: duplicate YAML keys were silently accepted

`kind: Secret` followed by `kind: ConfigMap` decoded to the last value, while the original bytes
survived for a downstream reader to interpret differently.

**Decision:** refused at any depth under `resources/`. The parser is now `go.yaml.in/yaml/v3`'s node
API, which also refuses anchors, aliases and merge keys.

## The layout question

The review's remaining points mostly traced back to one thing: v1 decided what a file is from its
extension. A YAML list was refused, a top-level `sops` key reserved that name in ordinary
configuration, and a Secret renamed to `.txt` was copied unread. The maintainer's view: an
extension says how bytes are encoded, not whether they are a Kubernetes resource, so stop guessing.

**Decision (maintainer): layout v2.**

- A settings folder has `resources/` (Kubernetes resources: parsed, checked, ConfigMaps turned into
  files) and `raw/` (anything: never read). Any other top-level entry is refused, with a message
  naming both. The image holds both at the same paths, plus `configmaps/<name>/<key>`.
- The name is `resources/`, not `krm/`: "KRM" is not a commonly known term.
- Secrets are resources: their name and namespace are readable, so the identity of every resource
  must be plaintext. SOPS's default (encrypt everything) is therefore refused; use
  `encrypted_regex: ^(data|stringData)$`.
- Secret checking is a **scoped** safeguard: a plaintext Secret under `raw/` is not read. That is
  the deal `raw/` offers, and the docs say so.
- ConfigMaps become files by default; the annotation `settings-image.configbutler.ai/files: "false"`
  keeps one a resource only. This replaces `--no-files`, so the digest depends on the folder alone.
- Two resources with the same group, kind, namespace and name are refused. No index file is
  written: a reader lists `resources/`.
- No v1 writer is kept: nothing used v1 outside this repository.

## The review's other points

| Point | Decision |
|---|---|
| Namespace is ignored in `configmaps/<name>/`, so two same-name ConfigMaps merged their keys | Refused outright in v2; the message suggests the annotation |
| Refuse two writes to one path; preserve formatting; require string `data` and base64 `binaryData`; no files from a SOPS ConfigMap | Kept |
| The build does not enforce all Kubernetes rules (1 MiB, name constraints) | Stated as such: schema checks may come later as an optional lint, not now |
| `--no-files` still validated the derived view | Gone with the flag |
| The checks prove ciphertext-shaped content, not a valid MAC or decryptability | Stated in format-v2.md §4 |
| A Secret renamed to `.txt`, passwords in a ConfigMap, `.env` files, private keys | Not a secret scanner: the docs say what is checked, `resources/` only |
| A production consumption example (who decrypts, where keys live) | Open |
| Custom resources: reader contract, duplicates, server metadata | Duplicates refused; the rest is the reader's, and `raw/` paths are how resources refer to files |
| Validate paths at the public `Build(Tree)` entry point | Open, independent of the layout |
| Ignored files enter an image attributed to a clean commit | Already decided in [first read §1](2026-11-02-first-read.md): the folder is packed as it is |
| Enforce the size limit before reading a file; a file-count limit | Open |
| Provenance is a claim, not authentication; "same folder, same digest" includes the source URL | Stated in format-v2.md §7 and §9 |
| `0644` stops direct execution only | Stated in format-v2.md §6 |
| The Action had no sensitive-kind input | Added: `sensitive-kinds` |
| Prioritise the conformance corpus, refusals and adversarial cases included | Still plan.md phase 2e |
